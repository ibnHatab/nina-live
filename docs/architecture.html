Nina: one log, two reasoning loops

Nina is a personal agent, and speech is one way to reach her. Everything that happens goes into one SQLite event log. The semantic world is rebuilt from that log. Metis reasons over it on its own clock, and pi does the open-ended work. Every tool is a member of one Metis composition.

The world is a function of its events, and nothing else

One SQLite file in WAL mode, append only. The seq orders it; at is world time, the now every world call already takes.

CREATE TABLE events (
  seq    INTEGER PRIMARY KEY,  -- the order replay trusts
  at     REAL    NOT NULL,     -- world time (s)
  stream TEXT    NOT NULL,     -- world | dialog | agent | task | prefs | sys
  kind   TEXT    NOT NULL,
  key    TEXT,                 -- entity/var, task id, utterance id
  cause  TEXT,                 -- the turn, tool call or rule behind it
  data   TEXT    NOT NULL,     -- JSON
  v      INTEGER NOT NULL      -- the kind's schema version
);
CREATE TABLE snapshots (seq INTEGER PRIMARY KEY, code TEXT, hash TEXT, blob BLOB);
CREATE VIRTUAL TABLE episodes USING fts5(text, kind, at UNINDEXED, seq UNINDEXED);

The determinism contract

  1. Time is an argument. The world never reads the clock, and semworld has no time.Now already. The old journal's wall-clock stamp goes with the store.
  2. No map order. Three loops in home.go (lines 345, 419, 458) walk Go maps; they move to sorted keys, so surprises replay in the same order.
  3. Listeners are pure. OnChange subscribers only read. Any write is an event.
  4. One writer. Only the apply loop changes the world. The feed, the tools and Metis append events.
  5. Tests hold it. Replay equals live at every checkpoint, golden logs replay to golden lines, and snapshot plus tail equals genesis replay. A new code version drops the snapshots and replays from genesis.

The other streams are episodic memory: dialog (heard, turn, said, cut, note, attention), agent (pi's message_end, replacing its JSONL sessions), task, and prefs. Every conversation is kept, for mining.

Metis is a second reasoning loop, not a tool

A tool runs when the LLM calls it. Metis beats on its own clock and on every change of the ports it reads, and its conclusions change what both LLMs know next. Each tool is represented in one hierarchical composition, metis-catalog's director lifted. A tool is not backed by a domain of its own.

Which pi mechanisms, and why

Steer, FollowUpyesmessages from outside the run: conclusions, outcomes, notes
TransformContextyes, read-onlythe current world projection before each request; it decides nothing

AfterToolCallnoa result already enters Metis, and so the log, through its effector

Autonomy: a rule whose conclusion needs deliberation emits task(goal, level), and Nina starts a pi run with no one having asked. If a task on the same specialists is already running, the conclusion is steered into it instead. Relevance comes from the composition: a task only receives the lines of the specialists it attended.

What checking the flows changed

  • Metis over TCP first: no. A world inside metis-home is written by metis-home, not by the log. A one-day spike over the old ports is fine to try Steer against a real run, but milestone 1 is in-process.
  • A ReasoningSystem interface maps onto what exists, with one call fewer:
    • Observe is an append.
    • Infer is the beat, which no LLM calls.
    • Snapshot is the projection, filtered to a scope.
    • Events is the log's subscription.
    • Validate is dropped: the verb is the check.
  • pi's listeners run on its loop goroutine (agent.go:701). The one that logs messages only queues them, and the SQLite write happens on the log's own goroutine.

The quantized port

Every world line carries its confidence P. The port quantizes it into the manifests' levels, unsure below 0.5, likely, and sure from 0.9, with a 0.05 hysteresis. A line goes on to the voice and to the tasks only when its value or its level changes. A belief wavering at a threshold, its age or its wording no longer says the same thing twice (port/).

Steer is what makes a task's answer complete

Each run is one pi task on a simulated home: the real composition and rules, a device that obeys after 1.5 s, and Gemini 3.8 Flash on OpenRouter. The four conditions switch pi's mechanisms on: none; TransformContext alone; Steer and FollowUp; all three. Run on 24 November, with the quantized port.

  • The world before each request saves calls: without it the model asked the home seven times for what one line tells, and once claimed a unit ran that was stopped.
  • Steer is what makes the night scene's answer complete: the lights', air's and TV's own lines arrive, and the task can say what each part did. Without it the check still passed, on the words alone, but the answer said the home "did not report any changes".
  • A person's change mid-run reaches the task only through the world's lines steered in. With TransformContext alone, the task answered before the change was in its context.
  • Still open: a call the rules refuse ("not confirmed yet") ends the task with "ask me again". A FollowUp on the confirmation helps when it comes before the end; a task cannot wait yet.
  • One run is one sample: the table shows what each mechanism makes possible, not a rate.
